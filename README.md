# SEXTANT

**개발 활동을 자동으로 기록해 개발 일지와 트러블슈팅 문서로 만드는 개인용 CLI.**

육분의(sextant)는 별을 보고 내 위치를 계산하는 도구다. 내가 쓴 코드를 관측해
내 좌표 — 무엇을 할 줄 아는지 — 를 알려준다는 뜻으로 붙였다.

> "나만의 AI 회사" 2호. 1호는 서버 모니터링 시스템 Sentinel.

---

## 왜 만들었나

매일 코드를 쓰고 문제를 풀지만 그 과정이 문서로 남지 않는다. 면접에서 "그때 어떻게
해결했냐"는 질문에 기억으로 답하게 된다. 커밋 메시지는 남지만 **왜 그렇게 고쳤는지,
무엇을 시도했다 버렸는지**는 어디에도 없다.

기록이 수동이면 안 쌓인다. 그래서 자동으로 만든다.

```
[코드를 쓴다] → [일지·트러블슈팅 자동 생성] → [사람이 검토·승인] → [포트폴리오]
```

---

## 지금 할 수 있는 것

Phase 0(수집)까지 동작한다. 일지 생성(Phase 1)은 작업 중이다.

| 커맨드 | 하는 일 | 상태 |
|---|---|---|
| `sextant init` | 현재 git 레포를 프로젝트로 등록 | ✅ |
| `sextant note "…"` | 자유 메모를 활동으로 저장 | ✅ |
| `sextant sync` | git log를 읽어 커밋을 활동으로 저장 | ✅ |
| `sextant log` | 하루치 활동으로 일지 초안 생성 | ⬜ Phase 1-B |
| `sextant show` | 생성된 일지 확인 | ⬜ Phase 1-B |
| `sextant approve` | 검토한 일지를 승인 | ⬜ Phase 1-B |

아직 **LLM을 호출하지 않는다.** 시크릿 스캐너(Phase 1-A)가 완성되기 전에는
외부로 나가는 경로를 만들지 않는다는 원칙 때문이다.


## 사용법

레포 안에서 등록한다. 하위 디렉토리에서 실행해도 레포 루트를 찾는다.

```bash
cd ~/projects/my-repo
sextant init
```

등록하면 작성자 분포를 보여준다. 한 사람이 회사 메일·GitHub noreply·개인 메일을
섞어 쓰는 일이 흔해서, **내 커밋이 남의 것으로 분류되고 있지 않은지** 이 시점에
눈으로 확인시킨다.

```
작성자 분포:
  ✗   20건  old-work@example.com
  ✓    1건  12345+me@users.noreply.github.com

✗ 표시된 커밋은 수집에서 빠집니다. 내 것이라면:
  sextant init --me old-work@example.com
```

커밋과 메모를 수집한다.

```bash
sextant sync                      # 내 커밋 전부
sextant sync --since 2026-01-01   # 소급 수집
sextant sync --all-authors        # 다른 사람 커밋까지
sextant note "락 경합 원인은 비관적 락 범위였음"
```

이미 수집한 커밋은 해시로 걸러지므로 몇 번을 돌려도 중복되지 않는다.

여러 레포를 등록할 수 있다. 각 레포는 독립된 프로젝트로 쌓인다.

## 어떻게 동작하나

```
sextant/
├── cli.py        커맨드 정의. 아래 계층을 잇기만 한다
├── config.py     ~/.sextant/config.toml — 레포↔프로젝트 매핑, 내 이메일 목록
├── collect/      git log 파싱, 메모 → 활동 변환
├── store/        저장 계층 (인터페이스 + SQLite 구현)
├── security/     시크릿 스캐너            (Phase 1-A)
├── llm/          Claude 호출, 스키마 검증  (Phase 1-B)
└── render/       마크다운 출력            (Phase 1-B)
```

데이터는 `~/.sextant/` 한 곳에 모인다 — `config.toml`, `sextant.db`, `logs/`.

### 설계 결정 몇 가지

**저장 계층을 인터페이스로 분리했다.** Phase 2에서 SQLite → PostgreSQL로 옮길 때
CLI·수집·LLM 코드를 건드리지 않는 게 목적이다. 그래서 인터페이스를 일부러 좁게
유지한다 — 편의 메서드 하나가 곧 이관 비용 하나다.

**시각을 세 가지로 나눠 저장한다.** 커밋 시각을 UTC로만 두면 KST 오전 8시 커밋이
UTC 전날 23시가 되어 **하루 전 일지에 들어간다.** 그래서 표시용(`occurred_at`,
원본 오프셋 보존), 정렬용(`occurred_utc`), 조회용(`local_date`, 원본 오프셋 기준
날짜)을 분리했다.

**신원을 레포가 아니라 사람 단위로 둔다.** 한 사람이 레포마다 다른 이메일로
커밋하므로, 레포의 `user.email` 하나만 믿으면 내 작업 대부분이 누락된다.

**조용한 누락을 만들지 않는다.** 작성자 필터로 제외된 커밋은 이메일별 건수를
전부 출력한다. 잘못 포함된 데이터는 나중에 눈에 띄지만, 빠진 데이터는 안 띈다.

## 보안 원칙

이 도구는 내 코드를 읽고, 나중에는 그 일부를 LLM에 보낸다. 그래서 규칙을
코드보다 먼저 정했다.

- **개인 레포만 대상.** 회사 업무 코드는 넣지 않는다.
- **패치 전문을 DB에 저장하지 않는다.** 커밋 메시지와 파일별 증감만 남긴다.
  diff는 커밋 해시로 필요할 때 git에서 다시 읽는다 — 같은 내용을 두 벌 갖지 않고,
  시크릿이 디스크에 한 벌 더 남지 않게 하려는 것이다.
- **LLM에는 전체 소스가 아닌 diff 요약만** 보낸다.
- 전송 전 **시크릿 스캐너**를 통과시킨다. API 키·토큰·private key·`.env` 패턴이
  검출되면 해당 hunk를 통째로 제외한다. *(Phase 1-A — 구현 전)*
- API 키는 환경변수(`ANTHROPIC_API_KEY`)로만 읽는다. 설정 파일에 쓰지 않는다.

## 자동 생성물의 취급

LLM이 쓴 문서는 전부 `DRAFT`로 저장된다. 사람이 읽고 고쳐야 `APPROVED`가 되고,
승인된 것만 내보낼 수 있다. 사실과 다른 서술은 면접에서 치명적이라 자동 생성물을
검토 없이 쓰지 않는다. 모든 문서에는 근거가 된 커밋 해시가 함께 남는다.

## 로드맵

각 단계가 끝나면 **그것만으로 매일 쓸 수 있는 도구**여야 한다. 다음 단계는 앞
단계를 2주 이상 실제로 써본 뒤에 시작한다.

| | | |
|---|---|---|
| Phase 0 | 수집 — 레포 등록, 커밋·메모 저장 | ✅ |
| Phase 1 | 기록자 — 일지·트러블슈팅 생성 | 작업 중 |
| Phase 2 | 프로필러 — 활동에서 역량 추출 | |
| Phase 3+ | 채용 매칭, 면접 질문 | |

Phase 2부터 Kotlin/Spring + PostgreSQL + pgvector로 확장할 계획이라, 지금도
저장 계층은 갈아끼울 수 있게 두고 있다.

## 개발

```bash
.venv/bin/python -m pytest          # macOS · Linux
.venv/Scripts/python -m pytest      # Windows
```

git 수집기 테스트는 임시 디렉토리에 실제 git 레포를 만들어 돌린다. `git log`
출력 형식과 타임존 처리가 파싱 대상이라, 가짜 문자열로는 회귀를 못 잡는다.
